1 · System architecture

Two managed planes. Telnyx Voice AI runs the phone call, the LLM and the workflow. Two Edge Compute functions hold the business logic and all state.

Telnyx managed (configured via REST) Our edge functions Stateful Actors KV

2 · Call flow: a booking call, end to end

The webhook runs once, at call start. After that, reads go to MCP. Writes go to scoped webhook tools: Telnyx adds caller_phone as a preset field the LLM never sees, and the route opens that caller's BookingActor.

3 · Conversation workflow (workflow.json)

9 nodes, 15 edges (the request path is drawn separately below). Prompt nodes have no default edge: the call stays on the node until the LLM picks a transition. Prompts come from prompts/*.txt, injected by assemble-workflow.ts.

speak (verbatim) prompt (LLM) / LLM-condition edge tool node / default edge

Every prompt node sees the 3 read-only MCP tools, because Telnyx attaches MCP servers to the whole assistant. The per-caller tools are shared webhook tools, listed in shared_tool_ids with tools_mode: "append": Receptionist gets get_appointment; Booking gets draft, status, book_appointment; Booking request gets draft, status, save_booking_request; Cancellation gets get_appointment + cancel_appointment.

Request path: online booking disabled

The only variable-comparison edge. It sits on Booking and is evaluated before the model's turn, so with the flag off the call never reaches a node that has book_appointment.

The server enforces it too: book_appointment reads the flag from KV on every call and refuses when it is "false", so flipping the flag mid-call can't sneak a booking through. Saved requests go to a clinic-wide BookingActor instance (clinic:callbacks) that staff read with GET /callbacks (Bearer STAFF_TOKEN).

4 · Where state lives

Three places, three lifetimes. Both functions read the same KV namespace (82be9f48…).

CallSession actor webhook

caller:+<phone>, one per caller, persists across calls

  • totalCalls: written by the webhook on every call
  • callerName, lastBookingId: nobody writes these (see §6)

BookingActor mcp-server

caller:+<phone>, one per caller, persists across calls (book on one call, cancel on the next)

  • draft: fields filled in order reason → preferredDate → slot → name
  • booking → BK-0001, or request → RQ-0001 when online booking is off
  • Single-threaded, so parallel tool calls can't overwrite each other

Callback queue mcp-server

The same BookingActor class, one clinic-wide instance clinic:callbacks

  • One entry per caller; a new request replaces the old one, cancelling removes it
  • An actor, not KV: concurrent appends are serialised instead of overwriting each other
  • Read by staff: GET /callbacks with Authorization: Bearer STAFF_TOKEN

CLINIC_KV

  • business_info: clinic config, the one source for both functions (seeded by seed-kv.sh)
  • online_booking_enabled: feature flag, defaults to "true"
  • webhook_calls/<phone>, webhook_errors: observability counters

In-process (mcp-server)

  • Business info and services cached at module level per instance, never refreshed
  • A new Store per request. MCP reads use no actor. Without an actor binding it falls back to in-memory Maps, used by tests only

Dynamic variables Telnyx

  • Set once by the webhook and fixed for the whole call
  • Defaults in setup.ts apply if the webhook fails or times out

6 · Gaps found while drawing

I checked each of these against the code. I haven't fixed any of them.

/metrics always reports 0 calls

handlers/metrics.ts:5 reads webhook_calls, but handlers/webhook.ts:28 writes only webhook_calls/<phone>. Nothing ever writes the total key.

webhook_errors misses real errors

It goes up only on an invalid payload. If the actor or KV throws, the request returns a 500 and the counter doesn't move, and those are the errors the "know within 1 minute" check depends on.

Returning-caller data never filled

Nothing calls updateCallerName or setLastBooking, so caller_name is always "". Bookings live in BookingActor and never reach CallSession.

Availability ignores existing bookings

check_availability (MCP) has no caller and reads no actor, so it offers every slot on the fixed grid, even ones already booked. Two callers can book the same slot. The fix would be a single clinic-wide calendar actor that reserves slots atomically.

docs/architecture.md is stale

It still describes an in-memory store keyed by phone, a func.toml for the MCP server, and Confirmation as a speak node. The code uses BookingActor, telnyx.toml with actors, and a prompt node.

Tool routes don't verify Telnyx signatures

POST /tools/* accepts any request, so anyone who knows a caller id could read or cancel that caller's appointment. Every Telnyx request carries telnyx-signature-ed25519 + telnyx-timestamp; verifying them with the account's public key would close it.

Webhook latency budget

Everything runs one after another: 2 actor calls, 3 KV reads and 1 KV write. That fits in 8 s, but it could get close to Telnyx's default of 1.5 s. Running the KV reads in parallel would cut it.
